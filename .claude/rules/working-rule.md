# 作業ルール

## コーディングルール

### タイプ安定性
* `any`禁止、やむを得ない場合`unknown`で受け取り、型ガードで絞ること
* すべての関数の引数と戻り値に明示的な型指定
* APIの応答（特にAI分析結果のJSON）は必ずZodなどでランタイム検証後にタイプ推論（z.infer）して使用 — AI出力はスキーマを破る可能性があるため、パース失敗時には明確にエラー処理
* `as` 型の断言は最小限にし、本当に必要な場合はその理由をコメントとして残すこと

### 커스텀 Hooks 적극 채택
* 컴포넌트 안에서 반복되는 로직(데이터 fetch, localStorage 접근, 폼 상태 등)은 즉시 컴포넌트 밖으로 빼서 커스텀 훅으로 분리
  * 예: useReports(), useAuth(), usePromptTemplate() 같은 형태로 관심사를 나눌 것
* 한 훅은 하나의 책임만 가지도록 유지 (예: 데이터 조회와 mutation을 억지로 한 훅에 합치지 않기)

### 테스트 작성 의무
* 핵심 로직(문장 분리, diff 계산, severity 판정, 카테고리 집계 등 순수 함수)은 반드시 단위 테스트 작성
* UI 컴포넌트는 최소한 렌더링이 깨지지 않는지 정도의 스모크 테스트는 포함
* 새 기능 추가 시 테스트 없이는 "완료"로 보고하지 말 것

### 커밋 메시지 / PR 규칙
* 커밋 메시지는 Conventional Commits 형식 사용: feat:, fix:, refactor:, test:, docs:, chore:
  * 예: feat: 방향 전환 토글 UI 추가, fix: auth/callback 라우트 405 에러 수정
* 한 커밋에는 하나의 논리적 변경만 포함 (기능 추가와 리팩토링을 섞지 않기)
* PR 설명에는 "무엇을 바꿨는지"뿐 아니라 "왜 바꿨는지"도 포함
