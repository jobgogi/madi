# 開発ルール（TDD）

`working-rule.md`의 "테스트 작성 의무"를 지키는 순서를 다음으로 고정한다.

## Red → Green → Refactor
1. **Red** — 구현 전에 실패하는 테스트부터 작성한다. 테스트를 실행해 실제로 빨간색(실패)
   상태인지 확인한 뒤 다음 단계로 넘어간다. 테스트 없이 구현 코드를 먼저 쓰지 않는다.
2. **Green** — 테스트를 통과시키는 데 필요한 최소한의 구현만 작성한다. 이 단계에서는
   설계를 다듬지 않는다 — 통과가 목표.
3. **Refactor** — 테스트가 계속 통과하는 상태를 유지하며 중복 제거, 이름 정리, 구조 개선을
   한다. 리팩터링 중 테스트를 수정해야 한다면 그건 리팩터링이 아니라 동작 변경이므로
   별도 Red 단계로 되돌아간다.

## 적용 범위
* `working-rule.md`가 테스트를 요구하는 대상과 동일: 순수 함수(문장 분리, diff 계산,
  severity 판정, 카테고리/통계 집계 등)와 스모크 테스트가 필요한 UI 컴포넌트.
* 타입 정의, 라우팅/레이아웃처럼 분기 로직이 없는 코드(리다이렉트만 하는 가드 등)는
  대상 밖 — 테스트할 로직 자체가 없기 때문. `basic-rule.md`의 판단 기준과 동일하게
  애매하면 먼저 보고하고 진행.

## 커밋 단위
* 가능하면 Red(테스트 추가, 실패 확인)와 Green(구현)을 같은 커밋에 묶어도 되지만,
  `git-rule.md`의 "한 커밋 = 하나의 논리적 변경" 원칙은 유지 — Refactor로 로직이
  바뀌면 별도 커밋으로 분리한다.
